# 活动重置功能 · 决策与实施日志

> 目标：为 9 类课堂活动（考试 / 智能练习 / 知识抢答 / 在线任务 / 随堂测验 / 代码练习 /
> 分组讨论 / 快速投票 / 课程练习）在"编辑、删除"之外增加**重置**能力——
> 清除活动关联的全部数据，保留活动内容本身。
> 权限：管理员可重置全部；教师只能重置自己创建的活动。

## 一、已冻结的口径（默认值，如需推翻请在对应步骤前提出）

| # | 议题 | 决策 |
|---|---|---|
| 1 | 题目算不算"数据" | 考试/练习/代码/投票的题属**内容**，保留；抢答 `quick_quiz_questions` 与课程练习 `ai_practice_keys` 提供勾选项"同时清空题目（重新抽题）"，**默认不清** |
| 2 | 活动状态 | 重置时**回滚到可重新参与态**（`ended→published`、`playing→waiting`、讨论 `ended→pending`，清 `started_at/ended_at`），并提供"仅清数据不改状态"选项 |
| 3 | 分组讨论分组 | `group_mode='auto'` → 连 `discussion_groups` 一起清（回到未分组）；`manual` → 保留组定义，只清 `members/messages/reports` |
| 4 | 积分 | 默认回收 `activity_rewards` 并重算 `student_total_points`；提供"保留已发积分"选项。**称号/徽章不自动降级**（仅在预览中提示将回收的分数） |
| 5 | 错题本 / 学习进度 | 默认联动清理，提供"保留错题本"勾选 |
| 6 | 确认强度 | 服务端必须先出**干跑预览**（受影响学生数 / 各表待删行数 / 将回收积分），前端要求输入活动标题二次确认 |

## 三、Step 1 实施记录

### 3.1 修复的两个口径缺陷

- **R-A 命名空间冲突**：智能练习与课程练习都往 `activity_type='practice'` 写流水，
  但 `activity_id` 分别是 `practice_sessions.id` 与 `knowledge_points.id`，两个 id 域重叠。
  后果不只是"按活动清理会互相误伤"，更严重的是 `award_participation/award_grade`
  的幂等检查会误判"已发放"——**学生参加完智能练习 #5 后再做课程练习知识点 #5，静默不加分**。
  写入侧已改为 `practice` / `course_practice` 分桶（`course_practice` 在
  `REWARD_CONFIG` 与 `ACTIVITY_TYPE_NAMES` 中早已存在，只是从未被写入过）。
- **R-B 抢答 activity_id 带前缀**：写入 `f"quick_quiz_{room_id}"`，清理侧一律按
  `str(room_id)` 匹配，两边永不相交 → **删除房间从不清理流水，排行榜长期虚高**。
  写入侧统一为 `str(room_id)`，删除侧同时兼容两种历史格式。

### 3.3 存量归位的保守原则

只有存在**行级正向证据**（该生该 id 有 `ai_practice_results` 记录）才改写为 `course_practice`；
证据冲突（同生同 id 既有会话答卷又有课程练习成绩）或无证据（会话已删除留下的无主流水）
一律**保留原样并计数告警**。
理由：一条流水只会因第一次事件产生，事后无法回溯归属，猜错就等于篡改另一个活动的积分。

## 五、Step 3 实施记录（重置 service · 注册表驱动）

### 5.1 交付物
`backend/activity_reset.py`（659 行，纯新增，**未改动任何现有行为**）：

| 对外接口 | 作用 |
|---|---|
| `describe_scope(type)` | 给前端渲染：该类活动保留什么、清什么、可勾哪些选项 |
| `preview_reset(type, id, options)` | **只读干跑**：将删行数、受影响学生、将回收积分、状态回滚计划、风险告警 |
| `execute_reset(type, id, options, operator, force)` | 执行并返回每步实际删除行数（供审计与回执） |
| `scope_keys()` / `ResetError(status_code)` | 类型枚举 / 业务异常（409 需强制、404 不存在） |

核心是 `RESET_SCOPES` 注册表：每个活动声明 `master(内容表) / targets(数据表) /
reward_types / notify_type / wrong_book_source / status / in_progress / runtime / keep`。
新增活动类型只需加一条声明，**不再抄第二遍删除逻辑**。

### 5.2 实现要点

- **预览与执行同一份口径**：`execute_reset` 内部直接复用 `preview_reset` 的计划，
  所以"预览看到的数字"就是"执行会删的数字"，不存在两套 SQL 漂移。
- **两库各自单事务**：`questions.db`（考试/练习/代码）与 `smartkb.db`（其余+积分+通知）
  分别原子提交，不假装跨库有事务；因此要求流程可重入 —— 重跑一次即收敛。
- **空表不发 DELETE**：预览计数为 0 的目标表跳过执行，审计回执里只留真实发生的删除。
- **只删数据行，绝不动内容行**：主表 `id / created_at / room_code / tasks.id(TEXT)`
  全部保留，学生端旧链接与统计口径不断裂。
- **派生重算**：删过积分流水就对**完整**受影响学生名单调 `update_student_total(check_upgrade=False)`
  （决策 4：不自动降级称号/徽章）。
- **运行时钩子**：抢答房间态只活在内存（`game_manager.rooms`），重置后必须 `remove_room`，
  否则旧分数会被再次广播回学生端。
- **进行中保护**：考试有 `in_progress` 答卷、抢答 `status='playing'` 时，不带 `force` 直接 409。

### 6.3 一个差点埋进生产的坑：ID 类型
`tasks.id` 是 **TEXT**（如 `root_AI作业_1779863308`），其余 8 类主键是 **INTEGER**。
SQLite 的 INTEGER 列与 TEXT 参数比较**不做隐式转换** —— 若路由把 `"6"` 原样透传，
表现会是"重置成功、返回 200、但什么都没删"，比直接报错危险得多。
对策：注册表声明 `id_kind`，入口 `_coerce_id()` 强制转换并在非法时 400。
（已用 E2E 验证：字符串 `"6"` 预览命中 1415 行、`"abc"` 返回 400、TEXT 任务 ID 原样命中。）

### 7.5 运维事故复盘：`--reload` 被前端构建打死
`uvicorn --reload` 默认监听整个仓库目录。`npm run build` 会一次性改写 `frontend/dist` 上百个文件，
触发重启风暴，reloader 卡死：端口仍在 listen、连接被 accept 后无人 read，累积 **120 个 CLOSE_WAIT**，
进程 0% CPU，所有 HTTP 请求超时。本任务中两次「卡住」皆源于此。
**对策**：`uvicorn backend.main:app --reload --reload-dir backend --port 8086 --host 0.0.0.0`，
前端构建不再触发重启；日志重定向到 `backend/logs/dev-server.{out,err}.log` 便于事后定位。
（改前端源码或 locales 后仍必须 `npm run build`，8086 直接服务 `frontend/dist`。）

### 7.9 顺带修掉的两个既有缺陷（都直接影响本功能的观感）

**D9 · 英文模式下 antd 组件内置文案不跟随语言**（`frontend/src/stores/localeStore.ts`）
`useLocaleStore.current` 写死 `'zh-CN'`，只有点语言开关调用 `setLocale()` 才更新；
而 `i18n` 用 `LanguageDetector(order:['localStorage'], lookupLocalStorage:'smartkb_lang')` 在启动时就恢复成英文。
于是**英文用户只要按一次 F5**，页面正文是英文、antd 内置部件却退回中文
（Modal 的"取消/确认"、表格空态、分页、日期选择…）。我的重置弹窗正是受害者：`取 消`。
修：初始值改为跟随 `i18n.language`，并订阅 `languageChanged` / `initialized` 同步回 store。
这是全仓级修复，不只服务于重置弹窗。

**D10 · 同一状态枚举在两个界面措辞不同**（弹窗 vs 活动列表）
列表页早有 `activityMonitor.status.*` 词表（9 项），我却另起炉灶建了 `reset.statusValue.*`（8 项），
结果 `active` 在列表叫 Active、在弹窗叫 In progress；更糟的是 `inactive` 我按字面猜成"未开始"，
而应用既有口径是"已停用"（任务下架义）—— **语义直接错**。
修：删掉 `reset.statusValue.*`，弹窗改为复用 `activityMonitor.status.*`，
并把后端中文兜底 `STATUS_LABELS` 也对齐同一套词（含 `finished`）。
再加一条审计断言：`reset.statusValue.*` 一旦重现即 FAIL，防止有人再养第二套。

### 7.10 测试纪律（本轮自己踩的坑，写下来防再犯）
本系统是**单点登录**：同一账号在别处登录会 bump `token_version`，把已存在的会话踢成 401。
本轮多次因为"浏览器工具 + headless 脚本 + python 脚本同时用 root 登录"而互相顶号，
表象是列表 `rows=0/1`、弹窗采样为空，一度被误判成"英文模式接口坏了"或"headless 渲染不出来"。
规则：**验证期间一个账号同一时刻只允许一个客户端**；跨工具验证要么串行，要么换不同账号。
另：`POST /api/auth/login` 实测 8~19s，脚本里的等待必须是"轮询 token 直到出现"，
固定 `sleep` 一定假失败（已按此改写回归脚本）。

### 8.6 通知的双语化（新增 payload 通道）
`notifications` 新增可空列 `payload`（沿用既有 ALTER 迁移风格）。重置回执写
`payload={"i18n":"activityReset","params":{"activity":<纯文本名>,"operator":<教师显示名>}}`，
`title/content` 保留中文原文给不识别该通道的老渲染器兜底。
新增 `frontend/src/utils/notificationText.ts`，铃铛与通知中心都经它取词。
实机（学生 s11001）：
- EN：`"[重置E2E] 一次性投票 …" has been reset by your teacher`
- zh：`「[重置E2E] 一次性投票 …」已被教师重置`
- 占位符/键名泄漏：0

这是设计内的兜底，不是回归。

### 8.7 仍需知悉的非英文点（数据，不是文案）

### 8.9 一次量级说明（避免误判为误删）
一次性投票"只删 2 条投票"却回执 `deleted_total=1410`，核对后确认无误：
`1410 = 全校用户数`，该投票 `target_scope=all`，发布时给每人一条通知，
删除范围 `source_type='poll' AND source_id=<本活动>` 精确命中这 1410 条。
**通知行数 ≈ 受众人数 × 事件数**，预览与执行同口径，故不是越界删除。
